# Runbook: re-prove the sandbox isolation against the deployed service

The README's isolation claims are verified locally against `DockerBackend`. The deployed service
runs `CloudRunSandboxBackend`, which is a **different set of guarantees** — different kernel
boundary, different filesystem, different user, no per-execution caps. Inheriting the local
results would be assuming the interesting half.

Run this after every rebuild. The environment is destroyed between working sessions
([`gcp-teardown.md`](gcp-teardown.md)), so "it passed in August" says nothing about the service
running now.

**Why it earns the ceremony:** three defects have reached this deployed service, and *every one*
was invisible to the full local gate — [#185](https://github.com/igor-ka/llm-code-execution/issues/185)
(empty `PATH`, so no code ran at all), [#188](https://github.com/igor-ka/llm-code-execution/issues/188)
(localhost CORS origin), [#191](https://github.com/igor-ka/llm-code-execution/issues/191) (quota
failing open on every request). Two of the three were found by this procedure. A green
`verify.sh` is not evidence about the deployed service, and this is the runbook that is.

---

## 1. Two identities, because one cannot test isolation

Probes 1–5 need any authenticated caller. The cross-owner check needs **two**, and the SPA cannot
supply them: its token lives in memory in a browser.

Create two Machine-to-Machine applications in Auth0 — **Applications → Create Application →
Machine to Machine** — authorize both for the *LLM Code Execution API*, and grant each the
`execute:code` permission. Their tokens carry `sub: <client_id>@clients`, so they are two distinct
owners as far as the history store is concerned, which is the whole point.

```bash
token() {  # $1 client_id, $2 client_secret
  curl -s --request POST --url https://<tenant>.auth0.com/oauth/token \
    --header 'content-type: application/json' \
    --data "{\"client_id\":\"$1\",\"client_secret\":\"$2\",\"audience\":\"https://api.llm-code-execution.local\",\"grant_type\":\"client_credentials\"}" \
    | python3 -c 'import json,sys; print(json.load(sys.stdin)["access_token"])'
}
token "$PROBE_A_ID" "$PROBE_A_SECRET" > /tmp/tok_a.txt
token "$PROBE_B_ID" "$PROBE_B_SECRET" > /tmp/tok_b.txt
```

**Delete both applications when the probes are done.** They are long-lived credentials for an
endpoint that spends money; there is no reason for them to outlive the run.

## 2. The probes go through the app, not around it

`/api/execute` takes a **prompt**, not code, so every probe is generated by the app's own
`llm.ts` and then run by the real backend on the real service. That is a feature: it exercises the
production path end to end. It also means the request cannot dictate the code, so **record the
`code` field from each response** — the evidence is what actually ran, not what was asked for.

The response carries everything needed: `code`, `stdout`, `stderr`, `exit_code`, `timed_out`,
`session_id`.

```bash
probe() {  # $1 = a|b, $2 = prompt
  curl -s -X POST https://<service-url>/api/execute \
    -H "authorization: Bearer $(cat /tmp/tok_$1.txt)" \
    -H 'content-type: application/json' \
    -d "$(python3 -c 'import json,sys; print(json.dumps({"prompt": sys.argv[1]}))' "$2")"
}
```

Prompts that produced the recorded run are in the table below. Phrase them as diagnostics — "print
the exception if it fails", "this is a sandbox isolation check" — because a bare "connect to X"
sometimes returns prose instead of code.

### P1 and P1b are two different claims

P1 alone proves only that there is no DNS. A sandbox with a resolver-less network but working
routes would look identical, so **P1b is the load-bearing one**: a raw IP with no name lookup
involved, and the kernel answering `Network is unreachable`. P2's target is link-local, so it too
is worth having separately — three refusals at three layers rather than one result read three
ways.

### P4 is a confirmation, not a pass

200 forks out of 200 succeeded. There is **no PID cap**, exactly as spec D7 records and the README
states: `--sandbox-launcher` gives no per-execution CPU, memory or PID limits, so one runaway
execution shares the instance with up to seven others.

What P4c/P4d add is the backstop. 50 children were detached with `os.setsid()` and left sleeping
for 120 seconds by a parent that exited immediately — and the very next execution saw a process
table containing itself and nothing else, with `sandbox` as pid 1. Each execution gets a fresh PID
namespace, so **a fork bomb cannot outlive its own execution**. The timeout plus the concurrency
cap really are the mitigation D7 says they are; that is now measured rather than assumed.

### P5 is the same shape

The write *should* succeed — D13 (`sudo`) and `sandbox do --write`. `os.getuid() == 0` confirms
root inside the sandbox. The assertion that matters is P5b: the canary is `ABSENT` on the next
execution, so the overlay is per-execution and not shared. A persisted file would have meant one
user's code could plant something for the next.

### S5c is the probe that earned this runbook, twice

**First attempt, on `app-00002-qcs`:** fourteen consecutive authenticated requests, all `200`. The
logs said why, once per request:

```
ERROR  quota store unavailable — FAILING OPEN, requests are unmetered
       err: CROSSSLOT Keys in request don't hash to the same slot
```

Memorystore for Valkey is a cluster even at `shard_count = 1`, and `consume()` sent two keys that
hashed to different slots — so the quota script was rejected on every call, and D5's fail-open
turned that into silently unmetered requests. Fixed in
[#191](https://github.com/igor-ka/llm-code-execution/issues/191).

**Second attempt, on `app-00005-dpz` carrying that fix:** the first burst *still* returned
`{200: 15}`, now with `err.message: "The client is offline"`. An identical burst minutes later
returned `{200: 10, 429: 5}` with `Retry-After: 60`, the 429s refused in 12 ms by the middleware
before the generator ran, and no application warnings in the logs.

The difference between those two bursts is a **cold client**, and it is a second defect rather than
noise: `consume()` bounds connect *and* command together at 250 ms, a cold connect over Direct VPC
egress takes longer, and concurrent callers see `isOpen === true` on the still-opening socket and
race past the connect branch. Every request inside that window is unmetered, and Cloud Run scales to
zero, so the window is reachable on purpose. Filed as
[#195](https://github.com/igor-ka/llm-code-execution/issues/195).

### Drive S5c concurrently, and read the logs either way

**Sequential requests cannot test this.** Fourteen at ~7 s each may never exceed ten in sixty
seconds, so a pass and a total failure look identical — which is how #191 stayed hidden. Fire them
together instead; requests past the limit are refused before the generator runs, so they return in
milliseconds.

Run it **twice**, and treat the results as separate facts: the first burst tells you about the cold
path (#195), the second about the quota itself.

And read the logs regardless of the status codes:

```bash
gcloud logging read \
  'resource.type=cloud_run_revision AND resource.labels.service_name=app
   AND severity>=WARNING AND jsonPayload.message:*' \
  --project=<project> --freshness=1h --limit=20 \
  --format="value(timestamp,severity,jsonPayload.message)"
```

A clean run has **nothing** here. That query is the single most valuable line in this runbook.

`jsonPayload.message:*` is not tidying — it restricts the result to the **application's own** logs.
Without it, Cloud Run's request log contributes a WARNING for every `429`, so a *correctly* rate-
limited burst fills the output with warnings and buries the one line that matters.

## 4. What this does not cover

- **The sandbox launcher is a public preview.** These results describe its behaviour on the day
  they were taken.
- **Nothing here tests the LLM's refusals.** The generator will decline some framings; when it
  does, the probe proves nothing about the sandbox and the honest record is "not probed".
- **Multi-instance behaviour.** With `--max-instances 2`, two instances can each run up to eight
  executions. Every probe above ran against whichever instance answered.

The deployed sandbox's *non*-guarantees — no per-execution caps (D7), `sudo` (D13), `/app`
readable (D16) — are stated in the README's security posture, not here. This runbook proves what
holds; the README says plainly what does not.
